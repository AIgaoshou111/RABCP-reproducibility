# L/C/G 单题评分细则｜修订稿，供作者检查

**用途。** 对一条计算机技术提问的可见文本打三个 0/1/2 分：L 看使用了怎样的技术语言，C 看给了多少与当前请求有关的背景，G 看希望回答完成什么任务。三维分别判断。它们是单次提问的观察值，不是提问者的真实能力等级。历史画像仍按论文原有方法更新；本稿不改公式、三维权重或五级状态。

## 需要改的三处

| 原评分提示词 | 问题 | 修订原则 |
|---|---|---|
| L=2“低频硬核术语” | “低频”取决于领域与时间；Docker 题里具体的机制关系可能没有罕见名词 | 看提问是否**具体使用或讨论技术机制、配置项或组件间关系**，不按词罕见程度评分 |
| C=2“标准 Bug Report 规范” | 只适合排错题；设计取舍和概念题未必有日志 | 看背景是否**足以定位当前请求并据此回答**，按排错、设计、概念等问题类型判断 |
| G=2“评估/分析层” | 问“为什么报错”可能仍只想修故障；出现“why”不等于研究机制 | 看**预期答案的主要任务**：基本说明、具体执行/排错，还是机制解释/方案权衡 |

## 统一判定表

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| **L：技术表达具体程度** | 只有日常表述，未明确使用技术对象、命令或概念。 | 使用工具、框架、命令、单个参数或一般技术概念，但没有展开具体机制或组件关系。 | 提问者具体写出了机制、协议行为、多个配置项的作用关系，或组件间的技术关系；必须能从原题指出对应片段。 |
| **C：与当前请求相关的背景** | 除请求本身外，几乎没有具体场景、约束、操作或观察。 | 有部分相关背景，例如环境、代码、报错、已尝试方法或设计目标中的一部分，但关键条件仍缺。 | 给出了足以定位请求的相关信息。排错题通常有环境/操作或配置，加上实际现象；设计题通常有当前结构、目标及重要约束。无需机械要求所有项目齐全。 |
| **G：希望回答完成的任务** | 索要术语含义、功能、基础用法或一般安装/设置说明。 | 要完成一个具体实现、操作或眼前故障的定位与修复。 | 明确要求解释运行机制、比较方案、评估利弊或作设计取舍；答案需给出理由或权衡，而非只给操作步骤。 |

## 判定顺序与边界

1. **先找主要请求，定 G。** 看提问者希望回答者最终交付什么。排错题中一句“为什么出错”通常仍为 G=1；若主要问题是“这两种架构应选哪种、为什么”，则为 G=2。“为什么”一词本身不决定档位。两个命令是否等价、某参数有什么用，是基本行为说明，可为 G=0；比较方案的后果与取舍才是 G=2。
2. **再看相关背景，定 C。** C 衡量可用背景，不衡量文章长度、提问质量或提问者能力。概念题简短可以是好问题，但仍可为 C=0。大段复制的日志若缺少问题目标和观察，也不自动为 C=2。对设计题，方案、目标和约束比错误日志更相关。
3. **最后看实际技术表达，定 L。** 产品名或框架名堆叠通常为 L=1。L=2 要能指出提问者写出的具体配置/机制，或组件怎样连接、交互；只列出方案名称仍可为 1。不能把回答者推断出的机制回填到原题，也不能仅凭罕见名词给 2。
4. **三维独立。** 高 L 不自动推出高 G；高 C 不自动推出高 L。复制来的代码、日志和术语可以反映这条提问提供了什么文本证据，但不能据此断言用户已经掌握它们。来源不明或截断严重、无法判断的文本应记录为“无法评分”并核查原题，不能自动填 0。
5. **多个请求时定主问题。** 先看作者明确要求解决的实际问题，再看标题与最后的直接问句。解释若只是为了修复当前故障服务，按排错给 G=1；如果作者要求比较并选择方案，按 G=2。两种请求确实并列、无法分出主次时，记录“多重意图”，按较低的 G 档给单一分数，避免仅凭一句机制疑问上调；保留另一请求的原文证据供后续人工核查。
6. **每维留证据。** L 记技术表达片段，C 记背景/缺失的关键条件，G 记核心问句。评分说明应能让另一人回到原文复核。标签只辅助检索原题，不能单独作为给 L=2 或 G=2 的证据。

上表是**细则核对用的边界案例**，不是新增实验准确率。抽查了 27 道原题，覆盖概念、排错、架构取舍和机制解释；三维规则能把“问什么”“提供了什么背景”“实际写出了什么技术信息”分开。H020、H048 说明修订后部分旧标签需按同一细则重核，不能把旧表直接当作新规则的标注结果。

## 论文表 3 的简洁英文写法

| Dimension | Score 0 | Score 1 | Score 2 |
|---|---|---|---|
| L: specificity of technical expression | Everyday wording without a clear technical object | Tools, commands, individual parameters, or general technical concepts | A concrete mechanism, interaction among settings, or technical relation between components articulated in the question |
| C: task-relevant context | Little information beyond the request | Some relevant setting, artifact, symptom, or constraint | Sufficient setting and evidence to locate the request, judged relative to the task type |
| G: requested answer | Definition, purpose, or basic usage, including basic command equivalence | Concrete implementation or immediate troubleshooting | Mechanism explanation, consequential option comparison, or design trade-off |

表 3 下方应补一句：**Scores describe the observable question, not the author's independently measured proficiency; L, C, and G are assigned separately from the question text.**

## 与代码及论文如何对齐

- 评分器输入应包含原题标题、正文及已核实的图片文字；提取的三个字段用于定位证据，不能代替原题。否则细则要求的“回到原文指出依据”无法执行。
- 自动评分输出除三维分数外，应各留一句原文依据；缺失、非法分数或原题截断时返回错误/待核查，不把它们默认为 0。
- 论文方法段、人工核验指南和评分提示词使用**同一张判定表**。当前投稿代码中的“低频硬核术语”“标准 Bug Report”与上表不一致；你确认本稿后，再统一代码与论文措辞。
- 本稿没有改变 `s_t=1+1.5G_t+0.25(L_t+C_t)`。G 仍表示主要请求的推理任务，L/C 表示文本表达与上下文；五级历史状态仍由连续更新产生，不由单题直接判定。
