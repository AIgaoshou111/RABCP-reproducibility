Looking at your configuration, the issue is that you're missing the database connection environment variables in your GitLab deployment. The `sameersbn/gitlab` image requires explicit database configuration through environment variables.

## Required Database Environment Variables

Add these to your GitLab deployment YAML:

```yaml
- name: DB_ADAPTER
  value: postgresql
- name: DB_HOST
  value: postgresql
- name: DB_PORT
  value: "5432"
- name: DB_USER
  value: gitlab
- name: DB_PASS
  value: password
- name: DB_NAME
  value: gitlabhq_production
```

## Why This Happens

The `sameersbn/gitlab` image doesn't automatically discover the PostgreSQL service. It requires explicit configuration through environment variables. When you ran it with docker-compose previously, these variables were likely defined in your docker-compose.yml file.

## Additional Issues to Check

1. **PostgreSQL Data Directory**: Your PostgreSQL deployment mounts the Gluster volume at `/var/lib/postgresql`, but the official postgres image expects data at `/var/lib/postgresql/data`. You should either:
   - Change the mount path to `/var/lib/postgresql/data`
   - Or set `PGDATA` environment variable to `/var/lib/postgresql`

2. **Shared Volume Conflict**: Both GitLab and PostgreSQL are using the same PVC (`gluster-dyn-pvc`). This could cause issues as both containers will try to write to the same volume. Consider using separate PVCs for each service.

3. **Database User Issue**: From your logs, the `gitlab` user exists but the database `gitlabhq_production` is owned by `postgres`. The GitLab image expects to connect as the `gitlab` user to the `gitlabhq_production` database. You may need to adjust ownership:
   ```sql
   ALTER DATABASE gitlabhq_production OWNER TO gitlab;
   ```
