```yaml
  value: "5432"

- name: DB_NAME
  value: gitlabhq_production
```

## About Your psql Test

The confusion with `psql -U gitlab` is expected behavior. The `-U` flag specifies the **username**, not the database name. When you don't specify a database with `-d`, psql defaults to using a database with the same name as the username. That's why it's looking for a database called "gitlab" - because you're connecting as user "gitlab" without specifying a database.

To test properly, use:
```bash
psql -U gitlab -d gitlabhq_production -h postgresql
```

## Additional Notes

1. **Service Discovery**: Your headless service (`clusterIP: None`) should work fine for DNS resolution within Kubernetes. The GitLab pod can reach PostgreSQL at `postgresql:5432`.

2. **Gluster Volume**: The shared Gluster volume shouldn't cause this specific issue. The problem is purely missing environment variables for database configuration.

3. **Redis**: Make sure you also have the Redis connection configured if needed. The `sameersbn/gitlab` image typically requires:
   ```yaml
   - name: REDIS_HOST
     value: redis
   - name: REDIS_PORT
     value: "6379"
   ```

After adding these environment variables, delete the existing GitLab pod and let it recreate with the new configuration.
