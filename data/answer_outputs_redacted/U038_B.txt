```yaml

  value: postgresql
- name: DB_HOST
  value: postgresql
- name: DB_NAME
  value: gitlabhq_production
- name: DB_USER
  value: gitlab
- name: DB_PASS
  value: password
```

## About Your Update 1

The `psql` command issue you're seeing is normal behavior. When you run `psql -U gitlab`, PostgreSQL defaults to using the username as the database name if no database is specified. That's why it's looking for a database called "gitlab" instead of "gitlabhq_production".

To connect to the correct database, you need to specify it explicitly:

```bash
psql -U gitlab -d gitlabhq_production -h 10.42.20.99
```

## Additional Notes

1. **Service Discovery**: Since you're using a headless service (clusterIP: None) named "postgresql", the GitLab pod should be able to resolve "postgresql" to the PostgreSQL pod's IP address. This is working correctly as shown by your successful telnet test.

2. **Gluster Volume**: The Gluster volume shouldn't cause this issue. The problem is purely the missing environment variables for database configuration.

3. **Redis**: Make sure you also have the Redis connection configured if you're using a separate Redis container. The `sameersbn/gitlab` image typically requires:
   ```yaml
   - name: REDIS_HOST
     value: redis
   - name: REDIS_PORT
     value: "6379"
   ```

After adding these environment variables, delete the existing GitLab pod and let the deployment recreate it with the new configuration.
